# 의사결정 기록 (Decision Log)

팀이 내린 결정과 **그 이유**를 남기는 문서다.

## 왜 기록하는가

1. 2주 뒤에는 아무도 "왜 그렇게 했는지" 기억하지 못한다.
2. 최종 발표에서 **"왜 이 데이터/모델/기술을 선택했나요?"** 는 거의 반드시 나오는 질문이다.
   이 문서가 그 답변의 근거가 된다.
3. 나중에 같은 논의를 반복하지 않게 된다.

## 작성 규칙

- **결정이 난 당일에** 기록한다. 몰아서 쓰면 이유를 잊는다.
- 검토했지만 **선택하지 않은 대안도 반드시 적는다.** 발표에서 가장 자주 물어보는 부분이다.
- 짧게 쓴다. 한 결정당 3~5줄이면 충분하다.
- 결정이 뒤집히면 기존 항목을 **지우지 말고** 새 항목을 추가한 뒤 기존 항목에 `→ DEC-00x에서 변경됨`을 덧붙인다.
- 누구든 결정에 참여했다면 직접 기록할 수 있다. 조장 전용 문서가 아니다.

## 결정 목록

### DEC-001. 협업 구조와 브랜치 전략

- **날짜:** 2026-09-30
- **결정:** 역할별 장기 브랜치(`eda`, `modeling`, `web`, `data-infra`)를 두고 `main`으로 PR 병합한다. 공통 문서는 `main`의 `docs/`에서만 관리한다.
- **이유:** 팀원 대부분이 Git을 처음 사용한다. 역할별로 브랜치를 고정하면 각자 작업 위치가 명확하다. 문서를 `main` 한 곳에 모으면 팀 간 인터페이스 합의를 모두가 같은 내용으로 볼 수 있다.
- **검토한 대안:**
  - 기능 단위 브랜치(GitHub Flow): 브랜치가 계속 늘어나 초보자가 현재 위치를 잃기 쉬움
  - 브랜치 없이 `main` 단독 사용: 한 사람의 실수가 전체에 즉시 반영됨
- **영향:** 장기 브랜치는 시간이 지나면 통합이 어려워지므로 **매일 1회 `main` 동기화**를 필수 규칙으로 둔다.

## 작성 양식 (복사해서 사용)

```markdown
### DEC-00X. <결정한 주제>

- **날짜:** YYYY-MM-DD
- **결정:** 무엇을 하기로 했는지 한두 문장
- **이유:** 왜 그렇게 정했는지
- **검토한 대안:** 무엇을 고려했고 왜 선택하지 않았는지
- **영향:** 이 결정 때문에 지켜야 할 것 / 달라지는 것
```
